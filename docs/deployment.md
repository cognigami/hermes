# Native macOS service packages

This is the authoritative package/lifecycle guide. [design.md](design.md) defines ownership and containment contracts; [development.md](development.md) defines development workflows. These assets are **not yet target-host qualified**. Script/plist tests and compilation do not certify launchd behavior, account permissions, machine restart or application containment. No privileged installation is authorized by this document.

It performs no host/resource discovery. This is not qualified host inventory or an admission override. No Linux persistent service, Windows, WSL or GPU package is supplied here.

The supported runtime boundary is synthetic leaf application and controller-helper processes. The controller does not own agent application processes, but does own its isolated validators and continuation adapters. Launchd default process-group cleanup remains enabled (`AbandonProcessGroup=false`); that is not general descendant containment or proof that a controller-owned child exited. Both controller and agent uninstall require the installed core's positive local quiescence check after bootout. An absent label, free authority lock, PID lookup or elapsed deadline alone cannot establish child exit. Unknown cleanup preserves the installation and state for recovery.

## Installation contract

All lifecycle commands below are explicit **privileged operator operations**, not commands run during ordinary development/tests. Use an already provisioned non-root account (for example `_hermes`). Account creation is outside the installer. Controller and agent use distinct fixed system-domain labels:

- `org.hermes.controller`
- `org.hermes.agent`

The generated plist sets `UserName` to that existing account, `RunAtLoad=true`, automatic `KeepAlive=true`, and a ten-second crash-restart throttle. It runs in the privileged `system` domain, independently of GUI login. The executable itself runs as the non-root service account. A launchd restart does not clear persisted controls or authorize replay of a started assignment.

From the **appropriate extracted package**, the argument contract is:

```sh
sudo sh ./install.sh USER INSTALL_DIR STATE_ROOT CA_SOURCE CERT_SOURCE KEY_SOURCE [entrypoint arguments...]
```

`INSTALL_DIR` and `STATE_ROOT` must be clean, absolute, dedicated paths, neither containing the other. The installation directory and every existing ancestor must be root-owned, not group/world writable, and contain no symlink components; writable home-directory ancestors are rejected even if the child directory is root-owned. The same checks cover installed binary, marker and plist before privileged lifecycle operations. Provision the installation parent explicitly before invoking the installer; it must already exist and pass that protection check. The state parent must also already exist and be traversable by the service account. The installer creates only the known leaf directories under a safe umask (077), explicitly sets their ownership/modes, then rechecks the privileged installation path before copying executable bytes and before registration. It never recursively creates or takes ownership of installation parents; a permissive caller umask does not weaken this contract. State/install roots must not themselves be symlinks (normal macOS `/var` ancestors are allowed for state only). Newlines/control characters in arguments are rejected. Use separate install/state directories for controller and agent. Do not use a shared/system directory as either root. The state directory is preserved, set to mode 0700 and owned by the service account; keep its ancestors traversable. The install directory, binary and installation metadata receive explicit root:wheel ownership and non-group/world-writable modes. Credentials are copied to `INSTALL_DIR/credentials/{ca,cert,key}.pem`, mode 0600, in a service-account-owned mode-0700 directory. The system plist is root:wheel mode 0644 and contains credential paths, never credential bytes. Protect source private keys separately; uninstall never removes those source files.

The installer supplies `--root`, `--ca`, `--cert`, `--key`; do not repeat those flags in entrypoint arguments. Each remaining argument is an individual plist `ProgramArguments` string, with no shell/eval. Current entrypoint-specific examples:

```sh
# Controller package; credentials need server-auth use and URL-matching identity.
sudo sh ./install.sh _hermes /opt/hermes-controller /var/lib/hermes-controller \
  /secure/controller-ca.pem /secure/controller-cert.pem /secure/controller-key.pem \
  --listen 127.0.0.1:8443 --workers synthetic-local --validator /opt/apps/hermes-synthetic-validator \
  --resource-policy /secure/controller-resource-policy.json

# Agent package; certificate identity must be worker:synthetic-local.
sudo sh ./install.sh _hermes /opt/hermes-agent /var/lib/hermes-agent \
  /secure/agent-ca.pem /secure/agent-cert.pem /secure/agent-key.pem \
  --worker synthetic-local --session provisioned-stable-session --host-id provisioned-host \
  --url https://localhost:8443 --runtime /opt/apps/hermes-synthetic
```

Examples describe current synthetic flags, not permission to deploy or expose LAN service. Supply an explicit controller resource-policy JSON file and an agent host identity matching that policy's host/worker approval. The policy separately approves host limits/baseline, assignment profiles and transfer/controller-helper reservations; observed host resources are not admission limits. Unknown hard tree-memory capability cannot satisfy a profile that requires it. No synthetic-backend override is supplied by these service examples. Provision correct CA chains, certificate purposes, URL identity and stable worker/session identities before installation. Do not include private data in argv. Installer scripts do not discover or invent resource policy/runtime interfaces.

Installation refuses a nonempty unmanaged directory or existing foreign plist/label. An identical repeated install leaves registration/disable intent unchanged, so reinstall does not silently undo intentional stop. Changed binaries, credentials or configuration require a verified uninstall before replacement; never overwrite a running binary. A partial failed installation is reported as failure and may require operator recovery of its known files; no automatic deletion of unknown content occurs.

## Intentional stop, start and uninstall

Operations must be operator-serialized: no concurrent manual starts, installers, uninstallers or edits of their managed files. This is a lifecycle assumption, not an interprocess orchestration lock.

```sh
sudo sh ./lifecycle.sh stop INSTALL_DIR STATE_ROOT
sudo sh ./lifecycle.sh start INSTALL_DIR STATE_ROOT
sudo sh ./uninstall.sh INSTALL_DIR STATE_ROOT
```

`stop` first disables the exact service, then boots out its registration and checks it is absent. Registration queries run under `LC_ALL=C`: only successful `launchctl print` means registered, and only exit 113 with the exercised exact-label two-line diagnostic (`Bad request.` followed by `Could not find service "<exact-label>" in domain for system`) means absent. Permission/IPC failures, another label, another exit code or unqualified OS diagnostics mean **unknown** and abort the operation. This classification also applies to fresh/repeated installation, explicit start and repeated uninstall; unknown status never licenses file removal or reports idempotent success. The diagnostic was observed in an authorized read-only native query, not a service installation/stop/start exercise. It does not use `launchctl stop`, which can immediately restart a KeepAlive job. Disable intent persists until explicit `start` enables and registers that same managed plist. A bare process signal is not intentional persistent stop. `start` does not reopen controller/agent run-control barriers; operational `resume` remains a separate authenticated control operation.

A service stop is **not** a completed application drain. Before normal agent uninstall, use authenticated worker/run drain and wait for confirmed execution quiescence and result/remainder reconciliation. Controller uninstall must also establish exit of its own validators/continuation children; it does not establish quiescence of remote agents. Retained unpublished bytes may coexist with positively proven quiescence and must be preserved.

Uninstall disables/boots out first, then invokes the appropriate installed binary's read-only `check-quiescence --root STATE_ROOT` for **both** service kinds. Only exit zero licenses file removal. The version-1 JSON result reports `state` and an optional `reason`; the controller also reports `unresolved_children`. An active authority/root lock reports `busy`; missing/incomplete metadata or unproven started-child exit reports `uncertain`, nonzero. The controller inspects its committed child-claim metadata under exclusive authority without opening normal controller authority, initializing/repairing metadata or inferring exit from parent disappearance. The agent retains its journal-specific positive leaf-quiescence rules. Unknown/busy results leave binary, credentials, plist, marker and state available for recovery; scripts do not clear markers, signal discovered PIDs or manufacture terminal evidence. Do not create an empty journal, checkpoint/repair metadata manually or change identities to bypass this gate. Original assignment ownership is unchanged by uninstall.

After successful verification, only the known installed binary, three copied credential files, installation marker and exact service plist are removed. Empty installation directories may be removed; unknown files are left intact. The spool/state root, unpublished and accepted result bytes, identities, journals, SQLite database and recovery records are never deleted. There is no purge operation. Repeated uninstall succeeds once the managed installation and registration are absent. Errors stopping services or checking quiescence are failures, not cleanup success.

Controller inspection reads a nonempty WAL through read-only SQLite access; it never uses `immutable` to ignore committed WAL records. With exclusive authority held, an absent/empty WAL and no nonempty rollback journal permit a checkpointed-main-database read without sidecar writes. Recovery-needed journals, unavailable WAL-index access, unknown schema/proof records or unreadable metadata remain uncertainty, not permission to initialize or repair the database.

The quiescence result is a snapshot: core lock is released before script deletion. The supported serialization rule excludes a concurrent manual restart in that interval. It does not claim an atomic check/delete primitive or safe operation against an adversarial concurrent launcher.

Bounded phases cover identical repeat installation; controller-only failure/restart while the agent retains issued computation; exact leaf-validator cleanup via a lifetime-held fixture lock; drain and positive packaged inspection; persistent stop over a bounded observation interval, explicit start retaining pause and separate authenticated resume; a non-destructive fixture child holding the existing root lock to prove busy uninstall preserves files; then release, positive inspection, repeated uninstall and reinstall preserving identity/results/accepted prefix. The validator is a leaf mode of the same fixture executable, verifies pinned synthetic identities and exact result bytes, and spawns no validator child. No journals or markers are altered by the lock test. Busy refusal requires an actual schema-version-1 inspector `busy` JSON record plus the expected core/script gate diagnostics, with the exact fixture lock held before and after the invocation. State/results and installed recovery-file byte digests are compared immediately before/after that refused uninstall; an IPC, permission or plist error before inspection cannot pass as busy evidence. The leaf-validator cleanup proof starts its entire submission/lock/stop/release deadline before submission and must finish within four seconds, shorter than both the fixture's five-second natural delay and the controller's five-second validator timeout; a late or no-op stop is inconclusive/failing, never cleanup success. Timeout/failure cleanup stops only trial-installed matching labels, preserves all recovery files and reports incomplete; successful trials retain state and a bounded evidence marker. The helper uses a 180-second exercise budget and a separate 30-second cleanup budget. Its own synchronous shell/foreground-utility commands run in newly owned process groups: cancellation kills that narrow group, waits/reaps the direct command and bounds inherited-output pipe waiting to 250 ms. INT/TERM cancel orchestration; the script forwards interruption to and waits for its exact helper child before cleanup. This is not generic process-tree containment or a claim about detached/setsid descendants; validator leaf signal behavior remains ordinary termination.

Actual agent-service crash with intact uncertain-journal uninstall is intentionally omitted, rather than stranding an installation with no supported reconciliation path. Separate process tests are not actual service-crash evidence. System-domain/UserName configuration and live service behavior do not establish empirical reboot/logout startup: no reboot, logout, foreign-job control, research access or remote operations are included. Actual privileged execution still requires the operator's explicit command; no privilege probe or service operation has been run during fixture development.
