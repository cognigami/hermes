- `docs/design.md` is authoritative for architectural and behavioral contracts. `docs/implementation-plan.md` owns proposed sequencing and temporary task progress. `docs/README.md` is only a current project summary and documentation index.
- Keep historical investigations, trial observations and design provenance in `docs/distributed-execution-discovery.md`; historical Perry failure analysis belongs in `docs/wp05d-distributed-compute-lessons.md`. Do not add conversation history, superseded proposals or task journals to the README or current design.
- Update the authoritative subject documentation as part of a contract change; do not maintain competing accounts in task notes or the index.
- Reuse from Dagu is optional. Do not introduce an adoption milestone, dependency or copied source solely because discovery evaluated it. Preserve applicable licensing obligations if code/tests are incorporated.
- Use supported project workflows through the provided development tools. Do not claim commands exist before their manifests/recipes are introduced and checked.
- Keep checks application-neutral and supplied-input/synthetic unless explicitly authorized otherwise. Documentation and implementation plans do not authorize deployment, sibling-project agent contact, research-data access or Kaggle submissions. Never use a running Perry study as a smoke-test fixture.
